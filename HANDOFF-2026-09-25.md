## 2. THE DISCOVERY — the free model gateway

**Endpoint:** `https://opencode.ai/zen/v1/chat/completions`
**OpenAI-compatible, no API key, billed at zero.**

```
curl -X POST https://opencode.ai/zen/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"space-bunny-free","messages":[{"role":"user","content":"say OK"}],"max_tokens":8}'
→ HTTP 200 in 1.11 s
{"choices":[{"message":{"content":"ZEN_OK"}}],"cost":"0"}
```

`GET https://opencode.ai/zen/v1/models` → **81 models** (claude-fable-5,
claude-opus-5, gemini-3.6-flash, gpt-5.6-sol, gpt-5.5, … plus the free roster).

`https://models.opencode.ai` is models.dev (HTML, not an API).
`https://api.opencode.ai/*` → `Not Found` (not the gateway).
`https://opencode.ai/api.json` → 404.

### The two gates (both measured, both real)

**Gate 1 — model gate (403).** From a normal host, keyless:

| model | HTTP | body |
|---|---|---|
| `space-bunny-free` | **200** | real completion |
| `mimo-v2.6-flash-free` | 403 | `FreeTierError: OpenCode's free tier can only be used from within OpenCode` |
| `nemotron-3.5-lightning-free` | 403 | same |
| `nemotron-3-ultra-free` | 403 | same |
| `ling-3.0-flash-fin-free` | 403 | same |
| `big-pickle` | 403 | same |
| `muse-spark-1.2-contributor-free` | 500 | server error |
| `muse-spark-1.3-contributor-free` | 500 | server error |

Only **1 of 8** free models answers a raw HTTP call. The other 7 require being
*inside* the OpenCode client — running them through `opencode run` satisfies that.

**Gate 2 — IP gate (429).** The same `space-bunny-free` call from **inside a
Cloudflare Worker**:

- Worker → Zen: **HTTP 429 `FreeUsageLimitError` on 6/6 attempts**
- This machine → Zen: **HTTP 200 on 6/6 attempts**
- Worker with 4 different User-Agents (workerd default, Chrome, empty, curl):
  **4/4 → 429**

So it is the **egress IP**, not headers, not auth, not the model. Zen rate-limits
Cloudflare's IP ranges. **A Worker can never call Zen directly.** This is a
permanent architectural constraint, not a bug to fix.

## 3. THE ANSWER — the Hive relay (built this session)

**File:** `hive/hive-relay.js` — Node, ~220 lines, no dependencies.

An OpenAI-compatible server that sits on an unblocked IP in front of the free
roster, with model failover.

| endpoint | behaviour |
|---|---|
| `GET /health` | no auth — `{ok, uptime_s, served, models:8}` |
| `GET /v1/models` | auth — the 8 free models |
| `POST /v1/chat/completions` | auth — walks the roster until one serves |
| `POST /hive/run` | auth — **the build callback** (see §4) |

Auth: `Authorization: Bearer <HIVE_TOKEN>`, token in `.secrets/hive-token`
(64 hex chars, gitignored, chmod 600). Unauthenticated → **401** (verified).

Two backends per model, tried in order:

1. `viaHttp` → Zen directly (fast; works for `space-bunny-free`)
2. `viaCli` → spawns `opencode run -m opencode/<model>` (this *is* "within
   OpenCode", so it serves the 7 gated models)

Public exposure: **cloudflared quick tunnel**
`https://township-scale-western-luke.trycloudflare.com` → `127.0.0.1:8787`.
⚠️ **The hostname is random and changes every time the tunnel restarts.** It is
stored in the Worker secret `HIVE_URL`, so a tunnel restart **breaks every build
until `HIVE_URL` is re-put**. Replace with a named tunnel + stable DNS later.

## 4. THE BUILD PIPELINE — root causes found and fixed

The old pipeline ran generation inside `ctx.waitUntil()`. It does not work.

### Cause A — `waitUntil` dies at ~30 s  ✅ FIXED

Build **70**: started `21:37:38`, planner logged `Plan ready
(hive/space-bunny-free)`, outbound fetch killed at **`21:38:09` = 31 s**
(tunnel log: `Incoming request ended abruptly: context canceled`), then the code
writer fell through to Workers AI → `4006` daily quota.

**Fix:** the Worker no longer does the work. It inserts the `running` row,
returns **202 in 1 s**, and fires a quick kick at the relay
(`POST {relay}/hive/run`). The relay replies **202 immediately**, then in the
background POSTs `https://createstuff-api…/api/builds/:id/run`. That is an
ordinary long-lived request with no 30 s ceiling.

**Proven:** build **72** ran for **123.1 s** on that callback — well past the
old ceiling. The architecture works.

### Cause B — callback route behind the auth gate  ✅ FIXED

Build **71**: relay logged `[hive-run] 401 … {"error":"Unauthorized"}`.
The `/api/builds/:id/run` route was placed *below* `requireUser`, so the Hive's
bearer token never reached it.

**Fix:** moved the route to immediately after `/api/health`, above the gate. It
self-authenticates against `env.HIVE_TOKEN`.

### Cause C — my own 120 s timeout  ⚠️ FIXED LOCALLY, **NOT DEPLOYED**

Build **72**: planner succeeded via Hive, then `[hive-run] 502 123.1s` with
`4006: you have used up your daily free allocation of 10,000 neurons`.

123.1 s ≈ 3 s planner + **120 s** — exactly `AbortSignal.timeout(120000)` in
`openAiGen()`. Generating 8000 tokens takes longer than that, so the request was
aborted, fell through to direct Zen (429), then Workers AI (4006).

**Local edits made (in the working tree, NOT live):**
- `workers/createstuff-api/src/index.js` → `AbortSignal.timeout(600000)`
- `hive/hive-relay.js` → `viaHttp` timeout `90_000` → `600_000`
- `hive/hive-relay.js` → `[chat]` per-request logging (`model backend secs chars`
  and `[chat] FAIL …`)

**The live Worker is version `38d3425d-f749-43fe-9bcd-4000edc2c4da` and still
has the 120 s timeout.** It will keep failing large builds until redeployed.

### Cause D — Workers AI daily quota  ⚠️ ALWAYS THE FALLBACK

`4006: you have used up your daily free allocation of 10,000 neurons` resets
~20:00 UTC (≈ 4 pm ET). Every build that falls through to Workers AI fails
during the day. The Hive path must not fall through for *timeout* reasons.

## 7. Answering "how will this work for USERS?" — honest assessment

The free Hive is the right core, but the current shape does not scale yet.

**What is genuinely good:**
- The gateway is free, keyless and answers in **1.1 s**; `cost:"0"` is in the
  response body, not our claim.
- 81 models are listed; 8 are free.
- Failover across models is implemented in the relay.

**What is NOT scalable yet (do not oversell):**

| issue | today | at 1 000s of users |
|---|---|---|
| relay runs on **this PC** behind a phone hotspot | works when online | ❌ dies if the PC sleeps; no SLA |
| quick-tunnel hostname is **random per restart** | must re-put `HIVE_URL` | ❌ unacceptable |
| 1 relay process, `served` counter, no queue, no concurrency cap | fine for 1 job | ❌ needs a queue + workers |
| gate 1: 7/8 free models only work via `opencode run` **spawn per request** | seconds–minutes | ❌ spawn cost per request won't hold |
| gate 2: Zen blocks datacenter IPs | why relay exists | any relay on a datacenter IP fails too |
| Workers AI fallback = 10 000 neurons/day | 1 build/day | ❌ cannot be the fallback at all |

**The honest scalable shape** (not built yet):
1. Relay moves off this PC to a small always-on host (VPS or a Cloudflare
   Worker in an *allowed* region — untested whether any Worker IP passes).
2. A **named** cloudflared tunnel → stable hostname, no secret re-put.
3. Add at least one server-side-friendly free provider key (OpenRouter
   `:free`, Gemini free tier) so the fallback is not Workers AI.
4. Queue + concurrency limit + per-user fairness in front of the relay.
