## 13. LATE ADDENDUM (2026-10-07, ~03:10) — fashionistas login was destroying itself

Complaint: the login was done *yesterday* and still had to be repeated every time, with no
guidance. Root cause was **client-side**, all in `fashionistas-ai/index.html`:

- old `:1459` — the shared `api()` helper turned **every** 401 into `toast("Session expired — please
  log in")` + `logout()` 600 ms later, and `doLogin()` posts through that same helper, so a wrong
  password signed you out and told you your session had expired;
- `grep -c "auth/me" index.html` → **0** — the stored session was never checked at boot;
- `afterAuth` stored `d.token` blind → the string `"undefined"` in localStorage →
  `Authorization: Bearer undefined` → 401 → straight back to the first bullet;
- after sign-in nothing said what to do next, and 402/503 were bare toasts with no action.

**Fix shipped `3cfe08b`** (pushed; live == `3cfe08b`, deployment `15ef54f1`, deploy
`scripts/deploy-local.sh` → `wrangler pages deploy . --project-name=fashionistas-ai --branch=main`):
auth-route 401s are reported as the credential error with the session untouched; every other 401 is
*confirmed* against `GET /api/auth/me` (auth gate before routing: valid token → **404**, dead/absent
→ **401**) before signing anyone out; anonymous 401 → "Sign in first to do that." with no toast;
`restoreSession()` runs once at boot; `afterAuth()` never writes `undefined` and toasts the next
step; 402 → `guideSubscribe()` → live `/pricing/` (**200**); 503 → names the missing keys.

**Proven in a real browser against the live site (4 tests):** sign-up → token **107 chars**, signed
in; **failed login while signed in → "Invalid credentials", session survives**; reload → still
signed in with `/api/auth/me → 404`; signed-out call → "Sign in first to do that." and **no**
"Session expired" toast. `npm test` → **267 pass / 0 fail**; ads unchanged (loader 1, `data-ad-slot`
